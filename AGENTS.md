# AGENTS.md
Guidance for AI coding agents (Claude Code, Codex) working in this repository.

## What this is

An unofficial **Travian T4** private-server clone (browser strategy game), forked from TravianX/ZravianX, with custom UI/gameplay changes and a Spanish translation. Legacy PHP `7.4` + Apache + MariaDB `10.6`, all provided via Docker. This is old procedural PHP with a thin class layer — expect string-concatenated SQL, `global` singletons, and no autoloader/framework.

## Running the project

Everything runs through Docker Compose (stack name `traviant4-php7`). The repo is bind-mounted into the web container, so **PHP edits are live with no rebuild** — only rebuild after changing `docker/Dockerfile` or `docker/php.ini`.

```bash
docker compose up --build --detach   # start / rebuild
docker compose ps                     # status (db must be "healthy")
docker compose logs --follow web db   # logs
docker compose down                   # stop, keep dbdata volume
./deploy.sh                           # git pull + rebuild (used on the prod box)
```

- Game: <http://localhost:8080/> · Installer: <http://localhost:8080/install/> · Admin: <http://localhost:8080/Admin/>
- MariaDB from host: `127.0.0.1:3308` (db `travian_t4`, user `travian`). Inside Docker the app connects to host `db` port `3306`.
- `reset_server.sh` wipes and reinstalls the game world from scratch (destructive).
- There is **no test framework and no linter**, but `tools/check_*.php` are standalone regression checkers: each one runs with `docker compose exec -T web php /var/www/html/tools/<name>.php` and exits non-zero on failure. Run them all after touching game logic, and add one alongside any non-trivial fix. Also verify changes by loading pages in the running container.

## First-time setup / DB schema

The DB schema and config are **generated by the web installer** at `/install/`, not committed. It writes `config/connection.php` (DB creds, gitignored), `config/config.php`, and `config/installed`. SQL schema changes live in `tools/migrations.sql`. MariaDB runs with `--sql-mode=` (non-strict) on purpose — the legacy schema relies on zero dates (`'0000-00-00'`) and loose inserts, so don't assume strict-mode behavior.

## Architecture

### Request flow
Each top-level `*.php` in the repo root is a full page (`dorf1.php` = village resource view, `dorf2.php` = village center/buildings, `dorf3.php`, `build.php` = single building, `hero*.php`, `karte.php` = map, `berichte.php` = reports, `nachrichten.php` = messages, `allianz.php`, `spieler.php` = profile, etc.). German-named files are a leftover of the Travian origin. `ajax.php` handles AJAX (`?f=` / `?cmd=` switch), `do.php` redirects, `login.php`/`anmelden.php` handle auth.

A game page typically: `include("GameEngine/Village.php")` → run game logic → then include a chain of `Templates/*.tpl` partials (`html.tpl`, `field.tpl`, `movement.tpl`, `production.tpl`, `troops.tpl`, `sideinfo.tpl`, `footer.tpl`, `header.tpl`, `res.tpl`, `vname.tpl`, `quest.tpl`).

### Bootstrap & global singletons
There is no DI. Including `GameEngine/Village.php` pulls in `Session.php`, which chains includes of `config/connection.php`, `config/config.php`, `Database.php`, the `Data/*` game tables, `Lang/<LANG>.php`, and the other engine classes. Several **global objects are instantiated at include time** and used everywhere via `global $...`:

- `$database` — `GameEngine/Database/db_MYSQLi.php` (`class mysqli_DB`, hundreds of query methods)
- `$session` — `GameEngine/Session.php` (login state, current village `$_SESSION['wid']`)
- `$generator` — `GameEngine/GeneratorX.php`
- `$logging` — `GameEngine/Logging.php`

When adding logic, follow this pattern (`global $database, $session, ...`) rather than introducing new instantiation.

### Database layer
`GameEngine/Database.php` switches on `DB_TYPE` (set in `connection.php`, `1` = MySQLi) and includes `Database/db_MYSQLi.php`. That file defines the `mysqli_DB` class **and**, at the bottom, legacy `mysql_query()` / `mysql_fetch_assoc()` / `mysql_num_rows()` / `mysql_real_escape_string()` / `mysql_error()` shim functions mapping the old `mysql_*` API onto the shared `$database->connection`. Legacy code across the repo calls these bare `mysql_*` functions directly — that's expected, not a bug.

### Config constants
`config/config.php` reads one row from the `config` DB table into `$result` and `define()`s the server constants used throughout the code: `SERVER_NAME`, `SPEED`, `LANG`, `WORLD_MAX`, `HOMEPAGE`/`SERVER` (public URL), `TB_PREFIX` (table prefix, e.g. `s1_`), protection timers, etc. Table names are always built as `TB_PREFIX . "tablename"`.

### Game data & logic
`GameEngine/Data/*.php` are static lookup tables (building costs `buidata`, units `unitdata`, resource fields `resdata`, hero `hero_full`, culture points `cp`, celebrations `cel`). Core mechanics: `Village.php`, `Building.php`, `Market.php`, `Technology.php`, `Battle.php`, `Account.php`, `Alliance.php`, `Ranking.php`, `Message.php`, `Inventory.php`, `Units.php`, `Profile.php`. `Automation.php` / `AutomationSinglePlayer.php` drive automated/bot behavior.

**Resource production has exactly one formula**, in `GameEngine/Production.php` (`villageGrossProduction()`): fields → bonus buildings (sawmill/brickyard/foundry, and grain mill + bakery added on top of the *fields*, never chained) → oasis → gold bonus → `SPEED`. Village, the raid path that tops up a village before it is looted (`Automation::updateRes`), the starvation check (`getCropProdstarv`) and the dorf3 overview all call it — never re-implement it locally, the copies used to drift and each one writes real resources. Anything that changes production while the owner is away — a field or bonus-building level, or the set of annexed oases — must call `Automation::accrueProductionBeforeChange()` first, so the new rate is not applied retroactively to the hours already elapsed.

**Crop has two numbers and they are not interchangeable.** Both live in `GameEngine/Production.php`:
- the **balance**, `Village::getProd('crop')` — gross + hero − population − troop upkeep, with the gold bonus. It is what dorf1 shows and the only thing starvation reads.
- the **free crop**, `villageFreeCrop()` — gross without gold and without the hero, minus **population only**. It is the only thing the build lock reads.

Free crop excluding troops is not an oversight, it is the official T4 rule: the lock exists so you cannot build yourself into a deficit *with buildings alone*, not to cap the army. A hammer at −5,000 crop keeps building, and pays for it through starvation instead. This repo used to subtract troops here, which locked whole villages out of construction, and used to cap troop training at `floor(balance / upkeep)` in `maxUnit()`, which official T4 does not do at all (that cap was also per-order, so repeating the order walked straight past it). Both are gone.

**The build lock is `Building::passesFoodGuard()` and it has five exceptions**, all of them load-bearing — without them a village can reach a state with no legal move: croplands always; grain mill and bakery when the upgrade *raises* free crop; main building level 1 always; main building, warehouse and granary up to level 10 once base crop production clears `freeCropUnlockThreshold(SPEED)` (276/h × SPEED — official states 276 on its speed‑1 worlds); and the World Wonder. Demolition is free except for grain mill and bakery, which cannot be torn down below free crop 1 — that is the same lock from the other side. The threshold is **≥ 1**, not ≥ 0. The master builder goes through the same guard: `dorf1.php`/`dorf2.php` queue through `masterBuildingRequest()`, which used to skip it entirely and made gold a way around the lock. Regression cover: `tools/check_build_food_guard.php`.

**Starvation is paced by the debt, not by the balance** (`Automation::starvation`). The granary going negative *is* the crop that went missing since the last sweep, so only enough troops die to cover that debt, each corpse refunds its training crop cost to the granary (legionnaire 30, trebuchet 90) exactly as in official T4, and the killing stops the moment the balance reaches 0 even if debt remains. Every one of those three matters: without the debt pacing, one minute in the red cost the same as ten hours; without the stop, a village nobody visited for a month would lose its whole army paying a debt official T4 would never have accumulated. **The debt is never carried over** — the granary is pinned at 0 whether or not anything died. It used to be carried when there was nothing left to kill, and five villages on the live world reached −47,000 crop that way: invisible to the player (`res.tpl` shows `max(0, crop)`) but enough to block training, building and every market send, because `deductResourcesIfAvailable` wants `crop >= cost`. Kill order is official: other players' reinforcements → your own troops sent from another of your villages → the home garrison, biggest army first and inside it the most numerous unit type. Troops in an annexed oasis count as being in the village (official says so); troops in transit or in someone's traps pay crop but do not die here, and neither does the hero. Caged animals (u31‑u40) never die of hunger because they never eat. Regression cover: `tools/check_starvation.php`.

**`vdata.pop` is an incremental counter, not a derived number** (`mysqli_DB::modifyPop`). Anything that rewrites `fdata` without going through it leaves a village eating crop for buildings that do not exist — which is where those −47,000 granaries came from. `tools/fix_village_pop.php` recomputes it from `fdata` (dry-run by default, `--aplicar` to write), system-account villages included — `natarVillagePopulation()` counts exactly the same slots, so the two converge instead of fighting.

**A village's population lives in 41 fields, not 40**: the World Wonder sits in `fdata.f99`, outside the range everything else uses. `villagePopulationSlots()` in `GameEngine/Production.php` is the only list, and `Automation::recountPop()`, `Automation::recountCP()` and `natarVillagePopulation()` all go through it. Building the Wonder does add its inhabitants — `buildComplete` calls `modifyPop` with whatever field the job carries, 99 included — so a recount that stopped at 40 did not merely skip it, it **deleted** it: one demolition or catapult hit in a Wonder village wiped the Wonder's whole population, its crop consumption and its culture points along with it. The production loops in that same file still run 1..40 on purpose — the Wonder produces no resources. Regression cover: `tools/check_wonder_population.php`.

**Oasis annexation has exactly one radius**, `Automation::oasisWithinAnnexationRange()`: a square of 3 tiles (not a circle of radius 3), wrapping at the map edge. The conquest path and the "other oases" table of the hero's mansion (`Templates/Build/37_heromansion.tpl`) both go through it — the mansion used to sort by euclidean distance and offer oases the game would then refuse.

**Taking an oasis is a hero job in a normal attack**, and `Automation::oasisAnnexationOutcome()` is the whole rule set: range first, then "already mine", then the three-oasis cap, then the Hero's Mansion (10/15/20 unlocks the first/second/third), and only then the loyalty roll — a rejected attack must never leave the oasis damaged. A **free** oasis falls to one attack; an occupied one costs `ceil(100 / (4 − oases the *defender's* village holds))`, which is the official table (holder with 3 → 1 attack, 2 → 2, 1 → 3), and taking it resets loyalty to 100. The **raid** gate lives in `sendunitsComplete()` next to the hero block: in a raid the hero loots and leaves, so farming an oasis with the hero in a farm list must not annex it behind the player's back. **Oasis loyalty regenerates at a flat 1 point per 30 minutes** (`oasisLoyaltyRegenerationRate()`) — the official rule is "the player cannot influence it", so unlike a village it reads no building level at all; it used to copy the village formula and heal 20× too fast behind a level‑20 palace and never at all without a residence. Regression cover: `tools/check_oasis_annexation.php`.

**A troop lives in exactly one of five places.** `units` (in its village) · `enforcement` (reinforcing another village or an oasis: `from` = home village, `vref` = destination) · `movement`+`attacks` (in transit, ida y vuelta) · `movement` sort_type 5/9 (settlers, hero on an adventure — no `attacks` row) · `prisoners` (caught in someone's traps). They are mutually exclusive — a troop leaves one in the same request it enters the next — so summing them never double-counts, and **anything that must account for every troop has to read all five**. `Technology::getAllUnits()` does, because crop upkeep and starvation must charge a troop wherever it is; `mysqli_DB::getVillageMovement()` covers the `movement` part and used to miss two of them (returning scouts, filtered out by an `attack_type != 1` that belongs to *display* code, and the hero on an adventure), so a village stopped paying for troops it still owned.

**The overview's troops tab (dorf3.php?s=5) deliberately reads only two of the five, and counts a troop where it *is*, not where it was trained.** Both tabs come out of `troopOverviewVillageGarrisons()` so they cannot disagree: "Tropas en aldeas" itemises every group hosted in each village (own troops, each player's reinforcements, annexed-oasis garrisons, caged animals) with its crop upkeep, and "Tropas propias" is the same list summed over the groups the viewer owns. So a village reinforcing another village *of the same account* shows its troops under the host, once — reading only `units` made them vanish from every row and the Total stopped being a total. Troops outside the player's own villages — reinforcing an ally, in transit, settling, captive — do **not** appear on this screen; the rally point's "Refuerzos" block is where official T4 shows them, and a report that they are "missing" here is that rule rather than a bug. Ids are absolute (u1..u50) in `units`/`enforcement` and tribe-relative (t1..t10, t11 = hero) in `attacks`/`prisoners`. Regression cover: `tools/check_troop_overview.php`, which pins the display rule, the tab-1-equals-sum-of-tab-2 invariant, and the upkeep rule.

**The grey zone is small here, and `GameEngine/GreyZone.php` says why at the top.** Official T4 draws a disc of radius 22; this world uses 6. The premium terrain that justifies the toll — 15-croppers and 50% oases — is written by the *map generator*, which runs once at install, so on a world already in play there is no reward at any radius; widening the disc would only tax players who settled before the rule existed. **A fresh world should set the radii to `0` and `22`**, where the installer seeds the good terrain inside and places starting villages far out.

Three details that are not obvious and each cost a debugging round:
- **The volcano is offset, not centred.** `GREY_ZONE_VOLCANO_OFFSET_*` moves its 5×4 footprint off `(0|0)`, because the installer puts the Natar capital there and Multihunter at `(1|0)`. Painting a volcano over a village leaves it invisible and unclickable; not painting it leaves a hole in the crater. The sprite keys are offsets *from the volcano's centre*, so anything converting them to map coordinates must add the offset back.
- **The volcano footprint is reserved scenery**: no oases, marked `occupied` so nobody founds or annexes on it. New worlds get that from `greyZoneTerrain()`; an existing world needs `tools/reserve_volcano.php`, which refuses to touch a tile holding a village or an *annexed* oasis.
- **Villages older than `GREY_ZONE_GRANDFATHERED_BEFORE` are never painted.** Their owners settled before the rule existed. It is purely cosmetic — waves only ever fire on *founding*, so nothing already built is affected either way.

Terrain, waves, tint and volcano all read the same constants, so moving them moves everything together. Regression cover: `tools/check_grey_zone.php`, whose geometry assertions adapt to whichever shape is configured.

**A building has one name, one gender and one icon**, all in `GameEngine/Catapult.php`: `buildingDisplayName()` (the list `Automation::procResType()` and `Building::procResType()` both delegate to — they used to carry identical copies, and the catapult target catalog a third that had already drifted, so the rally point offered "Excavación de barro" and the report then said "Barrera"), `buildingNameIsFeminine()` and `buildingDamageSentence()` (the adjective was hardcoded masculine, so nearly half the buildings reported "Barrera destruido"), and `buildingIconClass()`, which knows the two places the gpack's numbering does not match this repo's: the Herrería is gid 12 here and 13 in the art, and the Gran taller has no icon anywhere and falls back to `gebIcon`. Report rows carry **one icon per line** — with two catapult targets only the first building's icon was drawn, and it was labelled with a *unit* name (`Technology::unarray` is indexed by unit). Old reports stored the bare text, so `catapultReportInfoHtml()` still prepends the icon when the stored text has none. Regression cover: `tools/check_catapult_attacks.php`.

**"Not a player" has exactly one spelling**, `GameEngine/Accounts.php`: `isSystemAccount()` / `isPlayerAccount()` for PHP, `systemAccountSql()` / `playerAccountSql()` for queries, `natarsAccountId()` to resolve the Natar account, and `UID_SUPPORT`/`UID_NATARS`/`UID_NATURE`/`UID_MULTIHUNTER` instead of the bare ids. It is required from both `Database.php` (so the engine, the DB layer and the public pages reach it) and `Automation.php` (so checkers that stub the DB layer still get it). Never write the comparison inline — `tools/check_npc_accounts.php` scans every `.php`/`.tpl` and fails on a new one. Three things look like this boundary and are **not** it: `vdata.natar` (a Wonder-village marker), the tribe-4 fallbacks in `unknown_defender.tpl` / `defenders.tpl` (oases and caged animals), and the `$tid <= 4` comparisons in `Building.php` / `Automation.php` (resource field types).

**There are two kinds of NPC village, and the kind is per-village.** `vdata.npckind` (0 player, 1 static, 2 living), read through `isStaticNpcVillage()` / `isLivingNpcVillage()` in `Accounts.php` — never from the owner, because the `Natars` account owns both kinds. A missing column falls back to the pre-change behaviour, so an unmigrated world degrades instead of breaking. **Static** = the Wonder villages and the Natar capital: fixed garrison, no upkeep, no starvation, no growth. **Living** = the independent Natar villages of `GameEngine/NatarSettlement.php`: they pay crop, starve, grow and train like a player village.

**A living village's state is derived but never re-imposed.** Field and building levels *approach* the level their age allows (`min(ideal, current + repairSteps)`), so catapult damage persists and is rebuilt one level per `NATAR_SETTLEMENT_REPAIR_INTERVAL`. Writing the ideal unconditionally is the bug this replaced: a destroyed field came back within 60 seconds and catapulting a Natar village did nothing. For the same reason the **sustainable garrison and the training rate read the real fields, not the age plan** — that is what makes damage reach the troops. Consequence worth knowing: destroying wood/clay/iron fields *raises* the sustainable garrison, because population eats crop; only the crop fields starve it. Names are derived too, so the sweep repairs a stale one. They also build a **wall** (`NATAR_SETTLEMENT_WALL_TYPE`, a Muralla — T4.0 has no Natar wall building, only gids 31/32/33), which is the only reason a ram is worth sending at one; it lives in `f40`, outside the 19‑38 building strip, so `natarSettlementBuildingSlot()` places it and `natarSettlementPlannedSlots()` is what the growth loop walks. `Battle::wallFactors`/`battleWallDurability` key off the *defender's tribe*, so tribe 5 carries the Muralla's numbers; the static Wonder villages keep `f40 = 0` and are unaffected. An existing world gets its walls one level per repair interval, or all at once with `tools/fix_natar_settlement_walls.php`. **Conquest dissolves the garrison** rather than transferring it, after the ownership write succeeds — for every conquest, players included.

**A living village's state is derived, not accumulated** — field level from age, production from fields, sustainable garrison from crop, all a pure function of `(created, wref, now)`. Crop is the difficulty dial: nothing caps the garrison except what the fields can feed. Only `units` is real state (players kill troops), advanced toward the derived target under a compare-and-swap on `vdata.npcupdate`, with the catch-up clamped to `NATAR_SETTLEMENT_CATCHUP_CAP` intervals. **That clamp is not optional**: an unbounded quantity credited retroactively is exactly what emptied the Wonder villages once. Spawning hangs off the `addAdventures()` sweep pattern — no cron — and is anchored to player villages rather than spread uniformly like official T4, because this map has four players on 40,000 tiles. Names come from `natarSettlementName()` (seed-derived, so stable, with the coordinates appended for uniqueness) and **must never start with "Aldea"** — several listings prepend that word themselves. Regression cover: `tools/check_natar_settlements.php`, `tools/check_natar_settlement_combat.php`.

**A building is finished in exactly one place, `Automation::buildComplete()`.** The Plus "Completar" (finish every construction in the village for 2 gold) goes through `finishVillageConstructionsNow()`, which just pulls the jobs' timestamps forward and delegates. It used to carry its own copy — a hand-written `fdata` UPDATE plus `modifyPop` and `addCP` — and that copy had silently fallen behind on three things the real path does: `accrueProductionBeforeChange()` (so finishing a resource field with gold applied the new rate retroactively to every hour the player had been offline), `applyStorageCapacityDelta()` (so a warehouse or granary finished with gold never raised `maxstore`/`maxcrop`), and the culture increment (it added the level's *total*, the same bug that inflated `vdata.cp` world-wide). It also completed `master = 1` rows, which are *unpaid* master-builder requests — `MasterBuilder()` is what charges them on activation — so it checked the resources were there and never deducted them: free buildings for 2 gold. Only `master = 0` jobs are real constructions. Residence, Palace and the Wonder cannot be rushed, and a Wonder village cannot use it at all (and is not charged). Regression cover: `tools/check_gold_finish.php`, which mostly exists to fail if a second copy of the finish logic ever reappears.

**Demolishing has three official ways and one implementation.** From a Main Building at `DEMOLISH_LEVEL_REQ` (10) official T4 lets you tear a building down level by level with its timer, finish the level in progress with the gold finish-constructions feature (2 gold), or raze the whole building at once (5 gold — `Building::DEMOLISH_ALL_GOLD`, `Building::FINISH_ALL_GOLD` for the other). All three end in `Automation::demolishFieldLevel()`, the only place a level ever comes down: it accrues the old level's production before changing anything, moves `maxstore`/`maxcrop`, clears `fdata.fNt` when the slot empties and recounts population and culture points. The instant razing is that same step in a loop (`demolishBuildingNow()`), under the same per-village lock `addDemolition()` takes (`acquireDemolitionLock()`), and it charges only if a level actually fell — two clicks do not pay twice. The 2-gold finish already covered demolition but was **unreachable when a demolition was the only thing running**, because dorf1/dorf2 drew the queue box off `bdata` alone and the Plus page answered "nothing in progress"; both now count it, and the demolition shows as a row in the village's build queue like official. The food guard is the same lock from the other side: `demolitionAllowed($field, $targetLevel)` measures the mill and the bakery against the level that will *remain* — 0 for the full razing, not "one less" — and a Wonder village buys no gold shortcut here either. Regression cover: `tools/check_gold_demolition.php`.

**Culture points follow the official model exactly, and `buidata`'s two numeric columns do not mean the same thing.** `pop` is the *increment* a level adds; `cp` is the building's *total* CP/day **at** that level — embassy 20 = 153, academy 20 = 153, residence 20 = 77, resource field 10 = 6, the published official figures. `Automation::buildingCP()` therefore reads `tabla[level]` and `getPop()` returns `tabla[L] − tabla[L−1]` for the incremental `addCP()`; the two must agree, and `tools/check_culture_balance.php` pins that they do. Summing 0..N was the historical bug: it inflated passive CP by 1.5× with level-3 buildings and 4.4× with everything at 20 — the factor grows with level, so the world opened balanced and ran away on its own — and because both the incremental path and `recountCP()` made the same mistake, no recount ever contradicted the other. A `0.25` factor in `Hero.php` half-masked it and is gone.

The rest of the official model: **passive production does not scale with world speed** — the per-village requirement scales down instead. `$cp1` in `Data/cp.php` is the official x1 column and `$cp0` the official x3 one, both exact (village 2: 2,000 / 500; village 10: 251,000 / 83,500; village 50: 12,347,000 / 4,115,800); `$cp2` is invented by this repo, do not use it. `CP` in `config/config.php` picks the column, and this world **deliberately runs the x1 column on an x3 economy** — the one intentional deviation from official in the whole culture system. Official x3 pacing pins expansion at one village every ~5 days forever (the curve climbs almost as fast as production does), which is calibrated for gameworlds with thousands of players; this one has a handful, so the x1 curve makes it ~15 days and turns the Town Hall into a real decision. Passive production is **not** touched to compensate — it stays official and unscaled; the table is the only knob. Changing it on a live world is only safe together with `tools/rescale_culture_points.php`, which maps banked balances between the two columns in either direction without anyone gaining or losing a village slot; flip the constant and run the tool in the same move, or every account jumps three slots for as long as the two disagree. Only **fixed amounts** halve on a speed world — celebration caps 500/2000 → 250/1000, culture helmets 100/400/800 → 50/200/400, artwork cap 2000 → 1000 — plus the celebration's duration; `cultureFixedAmountDivisor()` is the single definition and the original game only ever had "normal" and "speed" worlds, which is why it is a halving and not a `/SPEED`. **A celebration pays production, not a flat number**: the small one grants the daily CP of the village holding it and the great one the daily CP of the whole account, each capped — same shape as the artwork, so a village producing 30 CP/day gets 30 from a small party, not 250. `celebrationCulturePoints($type, $production)` is the only definition and both the Town Hall page and `celebrationComplete()` go through it, so what is announced is what is credited. **A great celebration also moves conquest loyalty**, and the amount is absolute, not a percentage of the roll: +5 points per administrator when the village *sending* the chiefs is celebrating, −5 when the *target* is, so celebrations on both sides cancel. That sits on top of a per-tribe roll — Roman senator 20‑30, Teuton chief and Gaul chieftain 20‑25 (this repo used a flat `rand(15,25)` for all three, which took from the Roman exactly what makes it good at chiefing) — and the Teuton brewery then halves the total, because it cuts the chiefs' power of persuasion by 50% and belongs to the *attacker* (the building works account‑wide). Floor of 1 point per administrator. `Automation::administratorLoyaltyRange()` / `administratorLoyaltyCelebrationBonus()` are the only definitions; regression cover: `tools/check_conquest_loyalty.php`, which also pins the five conditions that block a conquest outright. Changing the requirement table on a live world **requires `tools/rescale_culture_points.php`** in the same move: it maps each banked balance to the same fractional position on the new curve, so nobody gains or loses a village slot. Without it every account jumps two or three slots at once. `tools/fix_village_cp.php` recomputes `vdata.cp` from `fdata`, which an existing world needs because the column is an incremental counter like `vdata.pop`.

**Conquering a village has one entry point and one cleanup, and both are load-bearing.** `mysqli_DB::applyConquestLoyalty()` does the ownership write and calls `conquestVillageCleanup()` in the same operation; `Automation::completeVillageConquest()` does the part that needs the engine (population recount, traps, prisoners, oases, hero). The official requirements are all in `getConquestEligibility()`: no Residence or Palace standing in the target (types 25/26 in fields 19‑38, at **any** level), not a capital, not the defender's last village, culture points for one more village (same `travianCultureExpansionEligibility()` the settler uses), and a free expansion slot in the *attacking* village — plus, in `sendunitsComplete()`, a **normal attack** (type 3, never a raid) with at least one administrator that neither died nor stayed in a trap.

What conquest does, all official and all pinned by `tools/check_village_conquest.php`:

- **Loyalty lands on 0, not on a cushion.** Regeneration is `loyaltyRegenerationRate()` = 2 points per 3 hours *per level* of the Residence/Palace, so a village whose administration building was just razed does not recover at all until the conqueror rebuilds it — that is the whole point of the rule, and this repo used to hand out 33 free points plus a 50% faster clock.
- **One administrator disappears, and only when the loyalty actually reaches 0.** Official: a chief that merely lowers loyalty comes home. Three chiefs in one wave roll three times and only the last one is spent.
- **The surviving army stays as the new garrison** (`stationConqueringArmy()`), as an `enforcement` row from the attacking village, hero included. There is no return movement, so the `attacks` row is deleted like the scenery path does. Consequence worth knowing: reinforcements eat the *host* village's crop, so a freshly taken village starts with a real deficit.
- **Everything that belonged to the village goes with it**: its garrison, its troops reinforcing elsewhere (`enforcement.from`), its troops in transit (sort_type 3 `from`, sort_type 4 `to`, settlers sort_type 5 `from` — the incoming attack being resolved is sort_type 3 `to`, so it is never caught), its training queue and its troops in someone's traps. Settlers in flight release the map tile they had reserved, or it stays `occupied` forever.
- **Academy research and smithy upgrades reset**, the build/demolition queues are cancelled, and the market offers, trade routes and farm lists of the old owner are deleted — otherwise the conqueror inherits the other player's target list and his routes keep shipping resources to enemy villages.
- **The wall always falls; tribe buildings only fall when the tribe changes.** The single list is `buildingTribeLock()` in `Catapult.php`, shared with `Building::isTribeBuildingAllowed()`. Razing buildings without `recountPop()` afterwards is the `vdata.pop` sin from the top of this file, so `completeVillageConquest()` recounts.
- **Annexed oases become independent** (`releaseVillageOasesSafely()`), they do not change hands with the village.
- **The hero dies if the taken village was its home village** (`conquestHeroCasualty()`), is pulled out of wherever it was standing, has any adventure cancelled and gets a new home village so it can still be revived. The player is told by message: a hero that dies in silence is a hero the player only finds out about days later.
- **Expansion slots the village had already spent stay spent** for the new owner (official), while the slot the *old* owner used to found it is freed.

**Wonder attack waves are scenery in both directions.** `startNatarAttack()` invents them with `addAttack()` and never deducts from `units`, so they must not return either — `sendunitsComplete()` skips the type-4 return movement when the attacking village is static NPC, and deletes the now-unreferenced `attacks` row. Deducting on departure would be wrong: the wave composition is a fixed table per Wonder level, not an army. And **conquest resets `npckind` to player** in the same write that changes the owner, or whoever razes a Wonder village's residence and chiefs it inherits a village exempt from upkeep and starvation. `tools/check_production_sanity.php` sweeps the world for the shape of the original bug: a static NPC village in the red, or any NPC village whose deficit exceeds what its own fields could produce at maximum level. Players may starve themselves — that is their call, and it is only reported.

**Natar villages are NPC garrisons, not simulated villages** — matching official T4, where Natar troops are static: never retrained, never reinforced from the capital, never starved. Their economy lives in `GameEngine/NatarVillage.php`; the installer and `tools/fix_natar_villages.php` both build them through `natarRestockGarrison()` + `natarProvisionVillage()`, never with hand-written SQL. Three rules follow and must not be "simplified" away:
- **NPC villages (owners 1–4: Support, Natars, Nature, Multihunter) pay no troop upkeep** in `Automation::bountycalculateProduction()`. Charged upkeep, a Wonder village produces ‑45k crop/h and the Natar capital ‑5.2M crop/h, against a ceiling of ~165k/h that no field layout can reach — so they can never hold crop and their garrison is on a countdown.
- **`starvation()` also skips owners 1–4**, belt and braces. Before that existed, the *first* attack on a Wonder village — a failed scouting run was enough, since `updateRes()` runs for every resolved attack — credited weeks of negative crop at once and starvation emptied the whole garrison in ~10 minutes, so the next attacker walked in without a casualty.
- **They must stay lootable**, as in official T4 where Natar villages are ordinary raid targets. `natarProvisionVillage()` puts all 18 fields at level 10 (the official Wonder-village layout) plus warehouse/granary, precisely so `stored − cranny` is positive; with the installer's bare 800 storage against a level‑10 cranny (10,000/resource here) every raid returned 0 forever.

Regression cover: `tools/check_natar_starvation.php`, `tools/check_natar_lootable.php`, `tools/check_natar_attacks.php`.

**Un mercader ocupado se cuenta con la Oficina de comercio de hoy, no con la del día en que salió el pedido.** `Automation::merchantsBusy()` es la única definición de "ocupado" y suma dos cosas distintas a propósito: `travelingMerchants()` (lo que ya está en el camino, ida y vuelta) con el número congelado al despachar — esa carga salió con los mercaderes que salió y no se re-reparte a mitad de viaje — y `offerMerchantsCommitted()` (lo que espera en una oferta publicada), que se **recalcula** con `merchantCarryCapacity()` de la aldea, igual que las rutas comerciales. La columna `market.merchant` se sigue escribiendo al publicar pero **nadie la lee**: leerla hacía que una oferta puesta sin Oficina y vendida con la Oficina a 20 apartara —y despachara— el triple de mercaderes de los que hacían falta, y que subir el edificio no liberara ninguno hasta cancelar y republicar. `acceptOffer()` calcula el envío del vendedor con **su** tribu y **su** Oficina (la aldea vendedora, no la del comprador que ejecuta el request), y la venta sale igual aunque al vendedor le hayan catapultado la Oficina después de publicar: rechazarla convertiría catapultear una Oficina ajena en una forma de congelarle todas las ventas. La función vieja `totalMerchantUsed()` fue **renombrada** en vez de extendida, para que cualquier llamada sin actualizar sea un fatal en lugar de contar de menos en silencio. Regression cover: `tools/check_market_offer_merchants.php`.

**El bono de la Oficina de comercio no es igual para las tres tribus.** Oficial desde T3.5: 10 puntos porcentuales por nivel para galos y teutones y **20 para romanos**, que es lo que compensa la debilidad romana del comienzo — con la Oficina a 20 el romano queda en 2500 por mercader, entre el galo (2250) y el teutón (3000), en vez de ser el peor de los tres para siempre. `bid28` guarda la columna oficial de galos y teutones (110..300) y `Automation::tradeOfficeBonusPercent()` deriva la romana (120..500) doblando el **bono**, no la capacidad: doblar la capacidad dejaría el nivel 0 valiendo 1000. Es la única definición, y la ficha del edificio (`Templates/Build/28.tpl`) la usa también para el porcentaje que anuncia. Regression cover: `tools/check_trade_office.php`, con la tabla oficial de los 20 niveles para las tres tribus.

### Templates
`.tpl` files are **plain PHP includes**, not a template engine — they mix HTML and `<?php ?>` and read the same globals. Edit them like PHP.

### Localization
`GameEngine/Lang/{es,en,de,ru,fa}.php` each define UI text as `define()` constants plus a `$lang` array. `es.php` (Spanish) is the active target locale; translation from the English original is an **ongoing effort** — player-facing pages are done, the Admin panel is the main remaining English area. Use neutral/LatAm Spanish, not peninsular terms.

### Admin panel
The **live** admin panel is `Admin/admin.php` → `Admin/Templates/`. The old duplicate entry points (`Admin/index.php`, `Admin/tpl/`, `Templates/Admin/`, …) were removed; if you find another copy, it is dead.

## Conventions & gotchas

- **Timezone is hard-coded** `America/Argentina/Buenos_Aires` (in `Village.php` and docker-compose), matching the Docker `TZ`.
- The web container runs Apache as **UID 1000** so it can write the bind-mounted code and `config/` / `install/installconfig/`. Permission errors on those paths usually trace back to a UID mismatch.
- `config/connection.php`, `config/installed`, `.env`, and `backup-*.sql` are gitignored; never commit generated config or secrets.
- Do **not** touch any sibling `travian-*` Docker containers on this host — only the `traviant4-php7` stack belongs to this project.
- Sidebar layout is fragile: never widen `#side_info` in `compact1.css` (it's a 196px float inside the 990px `#mid`, so widening it breaks the float layout). The signs *inside* it may overflow to the right, which is fine.
- **Wooden signs.** A sign's width used to be baked into its `gpack/.../img/layout/sign*.png` art. Three of them are now width-independent instead: `#villageList` (the village list), `#villageName` (the current village's name) and `#cultureProgress` (the culture panel, which borrows the village list art) all set `background-size:100% <h>px`, so the PNG stretches to whatever width the element takes. Consequences worth knowing:
  - Width comes from the content: `width:max-content` clamped by `min-width`/`max-width`. Keep the clamps within roughly ±25% of the art's native width or the nails start looking stretched.
  - `#villageList ul a:after{content:attr(data-name)}` is an invisible zero-height copy of the name in bold, so the measured width doesn't change with which village is active (the active one renders bold). Keep `data-name` in `Templates/multivillage.tpl` in sync with the link text.
  - `#villageName` grows in both directions: it's `left:85px` + `translateX(-50%)`, i.e. anchored by its centre rather than its left edge.
  - `#cultureProgress` builds the sign out of three real boxes (`.cultureProgressSign{Top,Body,Foot}` in `Templates/culture_progress.tpl`), with the body's negative margins reclaiming the parchment part of each roll. The container must stay backgroundless: the roll art is transparent outside the sign outline, so a background on the container shows through above the top roll and below the bottom one as a pale band. Its right edge must stay under x=293 of the viewport, where the leftmost dorf1 resource badge sits.
  - Both `#villageName` and `#cultureProgress` hang past the left edge of the 990px wrapper and get re-anchored by a `max-width:1119px` media query. That threshold is `990 + 2*maxOverhang + 20`: a media query measures the viewport *including* the scrollbar while the wrapper is centred in the width without it, so the breakpoint must also cover the scrollbar or the sign is clipped in a ~20px band of window widths.
  - Re-splice the art only if a sign needs a genuinely different native size: `tools/widen_sign.php <villages|vname> <ancho>` stretches the smooth parchment bands and leaves nails, screws and the arrow tip alone. It only stretches, never shrinks, and needs the original art restored first.
- **Commit style:** the commit must be **only a title** — short, in English, no body/description. The author is always the repo user (Matias); **never add a `Co-Authored-By` trailer or any other co-author**.

## Deployment note

Production is **travian.chewer.net**, served from a **Raspberry Pi 4B (8GB RAM)**, separate from local Docker. **Every push to git triggers `deploy.sh` on the Pi** (`git pull` + `docker compose up --build --detach`), so pushed changes go live automatically — treat `origin/master` as production. The redeploy is **near-instant**: the compose stack is just MariaDB + PHP and the game source is bind-mounted as a volume, so PHP/template edits apply immediately and the image only actually rebuilds when `docker/Dockerfile` or `docker/php.ini` change (rare, and the only case where the ARM/8GB slowness matters).

**Cloudflare sits in front of travian.chewer.net** and caches static assets for 4 hours (`cache-control: max-age=14400`). PHP output isn't cached, but CSS, JS and images are, so a deployed asset change is invisible until the TTL expires *unless the URL changes*. Every static asset referenced from a template or a stylesheet needs a version query when its content changes — including images referenced from inside CSS (`url(...png?v=N)`), which is the easy one to forget: bumping only `compact.css?asd…` ships new rules against stale art. To check what production is really serving, request the asset with a throwaway query (`?x=1`) to bypass the edge cache and compare against the plain URL; `cf-cache-status: HIT` in the headers means you're looking at the cache, not the origin.

**Never request the new versioned URL until the deploy has actually landed.** Fetching `…?v=37` while the Pi is still pulling caches the *old* file under the *new* key, and every player then gets new HTML against stale CSS for the full 4 hours — worse than not bumping at all. Poll the origin with throwaway queries first (`until curl -s '…/compact.css?bypass=$RANDOM' | grep -q 'v=37'; do sleep 4; done`), and only touch the real versioned URL once that passes. If a key does get poisoned, the self-service fix is to bump to a fresh one.

Schema changes that the installer would normally create must be applied to the prod DB manually (see `tools/migrations.sql`), and **a missed migration is silent**: the legacy `mysql_query()` returns `false`, nothing checks it, and the game reports success on a write that never happened (a missing `odata.conquered_at` made oasis conquest fail while the report still announced it). After every deploy that touches the schema, run `docker compose exec -T web php tools/check_migrations_applied.php`, which reads the idempotent statements out of `tools/migrations.sql` and verifies each one against the live database. Failed writes are now logged as `[SQL FALLIDO] …` by the DB layer, so `docker compose logs web` is where to look when something "worked" but changed nothing.
