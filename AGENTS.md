# AGENTS.md
Guidance for AI coding agents (Claude Code, Codex) working in this repository.

## What this is

An unofficial **Travian T4** private-server clone (browser strategy game), forked from TravianX/ZravianX, with custom UI/gameplay changes and a Spanish translation. Legacy PHP `7.4` + Apache + MariaDB `10.6`, all provided via Docker. This is old procedural PHP with a thin class layer — expect string-concatenated SQL, `global` singletons, and no autoloader/framework.

## Running the project

Everything runs through Docker Compose (stack name `traviant4-php7`). The repo is bind-mounted into the web container, so **PHP edits are live with no rebuild** — only rebuild after changing `docker/Dockerfile` or `docker/php.ini`.

```bash
docker compose up --build --detach   # start / rebuild
docker compose ps                     # status (db must be "healthy")
docker compose logs --follow web db   # logs
docker compose down                   # stop, keep dbdata volume
./deploy.sh                           # git pull + rebuild (used on the prod box)
```

- Game: <http://localhost:8080/> · Installer: <http://localhost:8080/install/> · Admin: <http://localhost:8080/Admin/>
- MariaDB from host: `127.0.0.1:3308` (db `travian_t4`, user `travian`). Inside Docker the app connects to host `db` port `3306`.
- `reset_server.sh` wipes and reinstalls the game world from scratch (destructive).
- There is **no test framework and no linter**, but `tools/check_*.php` are standalone regression checkers: each one runs with `docker compose exec -T web php /var/www/html/tools/<name>.php` and exits non-zero on failure. Run them all after touching game logic, and add one alongside any non-trivial fix. Also verify changes by loading pages in the running container.

## First-time setup / DB schema

The DB schema and config are **generated by the web installer** at `/install/`, not committed. It writes `config/connection.php` (DB creds, gitignored), `config/config.php`, and `config/installed`. SQL schema changes live in `tools/migrations.sql`. MariaDB runs with `--sql-mode=` (non-strict) on purpose — the legacy schema relies on zero dates (`'0000-00-00'`) and loose inserts, so don't assume strict-mode behavior.

## Architecture

### Request flow
Each top-level `*.php` in the repo root is a full page (`dorf1.php` = village resource view, `dorf2.php` = village center/buildings, `dorf3.php`, `build.php` = single building, `hero*.php`, `karte.php` = map, `berichte.php` = reports, `nachrichten.php` = messages, `allianz.php`, `spieler.php` = profile, etc.). German-named files are a leftover of the Travian origin. `ajax.php` handles AJAX (`?f=` / `?cmd=` switch), `do.php` redirects, `login.php`/`anmelden.php` handle auth.

A game page typically: `include("GameEngine/Village.php")` → run game logic → then include a chain of `Templates/*.tpl` partials (`html.tpl`, `field.tpl`, `movement.tpl`, `production.tpl`, `troops.tpl`, `sideinfo.tpl`, `footer.tpl`, `header.tpl`, `res.tpl`, `vname.tpl`, `quest.tpl`).

### Bootstrap & global singletons
There is no DI. Including `GameEngine/Village.php` pulls in `Session.php`, which chains includes of `config/connection.php`, `config/config.php`, `Database.php`, the `Data/*` game tables, `Lang/<LANG>.php`, and the other engine classes. Several **global objects are instantiated at include time** and used everywhere via `global $...`:

- `$database` — `GameEngine/Database/db_MYSQLi.php` (`class mysqli_DB`, hundreds of query methods)
- `$session` — `GameEngine/Session.php` (login state, current village `$_SESSION['wid']`)
- `$generator` — `GameEngine/GeneratorX.php`
- `$logging` — `GameEngine/Logging.php`

When adding logic, follow this pattern (`global $database, $session, ...`) rather than introducing new instantiation.

### Database layer
`GameEngine/Database.php` switches on `DB_TYPE` (set in `connection.php`, `1` = MySQLi) and includes `Database/db_MYSQLi.php`. That file defines the `mysqli_DB` class **and**, at the bottom, legacy `mysql_query()` / `mysql_fetch_assoc()` / `mysql_num_rows()` / `mysql_real_escape_string()` / `mysql_error()` shim functions mapping the old `mysql_*` API onto the shared `$database->connection`. Legacy code across the repo calls these bare `mysql_*` functions directly — that's expected, not a bug.

### Config constants
`config/config.php` reads one row from the `config` DB table into `$result` and `define()`s the server constants used throughout the code: `SERVER_NAME`, `SPEED`, `LANG`, `WORLD_MAX`, `HOMEPAGE`/`SERVER` (public URL), `TB_PREFIX` (table prefix, e.g. `s1_`), protection timers, etc. Table names are always built as `TB_PREFIX . "tablename"`.

### Game data & logic
`GameEngine/Data/*.php` are static lookup tables (building costs `buidata`, units `unitdata`, resource fields `resdata`, hero `hero_full`, culture points `cp`, celebrations `cel`). Core mechanics: `Village.php`, `Building.php`, `Market.php`, `Technology.php`, `Battle.php`, `Account.php`, `Alliance.php`, `Ranking.php`, `Message.php`, `Inventory.php`, `Units.php`, `Profile.php`. `Automation.php` / `AutomationSinglePlayer.php` drive automated/bot behavior.

**Resource production has exactly one formula**, in `GameEngine/Production.php` (`villageGrossProduction()`): fields → bonus buildings (sawmill/brickyard/foundry, and grain mill + bakery added on top of the *fields*, never chained) → oasis → gold bonus → `SPEED`. Village, the raid path that tops up a village before it is looted (`Automation::updateRes`), the starvation check (`getCropProdstarv`) and the dorf3 overview all call it — never re-implement it locally, the copies used to drift and each one writes real resources. Anything that changes production while the owner is away — a field or bonus-building level, or the set of annexed oases — must call `Automation::accrueProductionBeforeChange()` first, so the new rate is not applied retroactively to the hours already elapsed.

**Oasis annexation has exactly one radius**, `Automation::oasisWithinAnnexationRange()`: a square of 3 tiles (not a circle of radius 3), wrapping at the map edge. The conquest path and the "other oases" table of the hero's mansion (`Templates/Build/37_heromansion.tpl`) both go through it — the mansion used to sort by euclidean distance and offer oases the game would then refuse.

**A troop lives in exactly one of five places, and `GameEngine/TroopOverview.php` is the only thing that adds them up.** `units` (in its village) · `enforcement` (reinforcing another village or an oasis: `from` = home village, `vref` = destination) · `movement`+`attacks` (in transit) · `movement` sort_type 5/9 (settlers, hero on an adventure — no `attacks` row) · `prisoners` (caught in someone's traps). They are mutually exclusive, so summing them never double-counts. Two consequences that each cost a bug: reading only `units` — what the overview's troops tab used to do — makes an army reinforcing an ally, *or another village of the same account*, vanish from the game entirely; and **in-transit troops must be grouped by `attacks.vref`, not `movement.from`**, because `attacks.vref` is the home village on both legs of the trip (the return reuses the outbound `attacks` row), while `movement.from` misattributes a foreign reinforcement being sent back. (`mysqli_DB::getVillageMovement()`, the older helper that feeds crop upkeep, groups by `movement.from`/`to` instead, and gets away with it only because every creator in the engine happens to set them equal to `attacks.vref` — it is a coincidence to preserve, not a rule to rely on.) The overview's two tabs are the two groupings: "Tropas propias" by home village (the player's real army), "Tropas en aldeas" by location (what each village hosts and feeds, foreign reinforcements included). Regression cover: `tools/check_troop_overview.php`.

**The grey zone is small here, and `GameEngine/GreyZone.php` says why at the top.** Official T4 draws a disc of radius 22; this world uses 6. The premium terrain that justifies the toll — 15-croppers and 50% oases — is written by the *map generator*, which runs once at install, so on a world already in play there is no reward at any radius; widening the disc would only tax players who settled before the rule existed. **A fresh world should set the radii to `0` and `22`**, where the installer seeds the good terrain inside and places starting villages far out.

Three details that are not obvious and each cost a debugging round:
- **The volcano is offset, not centred.** `GREY_ZONE_VOLCANO_OFFSET_*` moves its 5×4 footprint off `(0|0)`, because the installer puts the Natar capital there and Multihunter at `(1|0)`. Painting a volcano over a village leaves it invisible and unclickable; not painting it leaves a hole in the crater. The sprite keys are offsets *from the volcano's centre*, so anything converting them to map coordinates must add the offset back.
- **The volcano footprint is reserved scenery**: no oases, marked `occupied` so nobody founds or annexes on it. New worlds get that from `greyZoneTerrain()`; an existing world needs `tools/reserve_volcano.php`, which refuses to touch a tile holding a village or an *annexed* oasis.
- **Villages older than `GREY_ZONE_GRANDFATHERED_BEFORE` are never painted.** Their owners settled before the rule existed. It is purely cosmetic — waves only ever fire on *founding*, so nothing already built is affected either way.

Terrain, waves, tint and volcano all read the same constants, so moving them moves everything together. Regression cover: `tools/check_grey_zone.php`, whose geometry assertions adapt to whichever shape is configured.

**"Not a player" has exactly one spelling**, `GameEngine/Accounts.php`: `isSystemAccount()` / `isPlayerAccount()` for PHP, `systemAccountSql()` / `playerAccountSql()` for queries, `natarsAccountId()` to resolve the Natar account, and `UID_SUPPORT`/`UID_NATARS`/`UID_NATURE`/`UID_MULTIHUNTER` instead of the bare ids. It is required from both `Database.php` (so the engine, the DB layer and the public pages reach it) and `Automation.php` (so checkers that stub the DB layer still get it). Never write the comparison inline — `tools/check_npc_accounts.php` scans every `.php`/`.tpl` and fails on a new one. Three things look like this boundary and are **not** it: `vdata.natar` (a Wonder-village marker), the tribe-4 fallbacks in `unknown_defender.tpl` / `defenders.tpl` (oases and caged animals), and the `$tid <= 4` comparisons in `Building.php` / `Automation.php` (resource field types).

**There are two kinds of NPC village, and the kind is per-village.** `vdata.npckind` (0 player, 1 static, 2 living), read through `isStaticNpcVillage()` / `isLivingNpcVillage()` in `Accounts.php` — never from the owner, because the `Natars` account owns both kinds. A missing column falls back to the pre-change behaviour, so an unmigrated world degrades instead of breaking. **Static** = the Wonder villages and the Natar capital: fixed garrison, no upkeep, no starvation, no growth. **Living** = the independent Natar villages of `GameEngine/NatarSettlement.php`: they pay crop, starve, grow and train like a player village.

**A living village's state is derived but never re-imposed.** Field and building levels *approach* the level their age allows (`min(ideal, current + repairSteps)`), so catapult damage persists and is rebuilt one level per `NATAR_SETTLEMENT_REPAIR_INTERVAL`. Writing the ideal unconditionally is the bug this replaced: a destroyed field came back within 60 seconds and catapulting a Natar village did nothing. For the same reason the **sustainable garrison and the training rate read the real fields, not the age plan** — that is what makes damage reach the troops. Consequence worth knowing: destroying wood/clay/iron fields *raises* the sustainable garrison, because population eats crop; only the crop fields starve it. Names are derived too, so the sweep repairs a stale one. **Conquest dissolves the garrison** rather than transferring it, after the ownership write succeeds — for every conquest, players included.

**A living village's state is derived, not accumulated** — field level from age, production from fields, sustainable garrison from crop, all a pure function of `(created, wref, now)`. Crop is the difficulty dial: nothing caps the garrison except what the fields can feed. Only `units` is real state (players kill troops), advanced toward the derived target under a compare-and-swap on `vdata.npcupdate`, with the catch-up clamped to `NATAR_SETTLEMENT_CATCHUP_CAP` intervals. **That clamp is not optional**: an unbounded quantity credited retroactively is exactly what emptied the Wonder villages once. Spawning hangs off the `addAdventures()` sweep pattern — no cron — and is anchored to player villages rather than spread uniformly like official T4, because this map has four players on 40,000 tiles. Names come from `natarSettlementName()` (seed-derived, so stable, with the coordinates appended for uniqueness) and **must never start with "Aldea"** — several listings prepend that word themselves. Regression cover: `tools/check_natar_settlements.php`, `tools/check_natar_settlement_combat.php`.

**Wonder attack waves are scenery in both directions.** `startNatarAttack()` invents them with `addAttack()` and never deducts from `units`, so they must not return either — `sendunitsComplete()` skips the type-4 return movement when the attacking village is static NPC, and deletes the now-unreferenced `attacks` row. Deducting on departure would be wrong: the wave composition is a fixed table per Wonder level, not an army. And **conquest resets `npckind` to player** in the same write that changes the owner, or whoever razes a Wonder village's residence and chiefs it inherits a village exempt from upkeep and starvation. `tools/check_production_sanity.php` sweeps the world for the shape of the original bug: a static NPC village in the red, or any NPC village whose deficit exceeds what its own fields could produce at maximum level. Players may starve themselves — that is their call, and it is only reported.

**Natar villages are NPC garrisons, not simulated villages** — matching official T4, where Natar troops are static: never retrained, never reinforced from the capital, never starved. Their economy lives in `GameEngine/NatarVillage.php`; the installer and `tools/fix_natar_villages.php` both build them through `natarRestockGarrison()` + `natarProvisionVillage()`, never with hand-written SQL. Three rules follow and must not be "simplified" away:
- **NPC villages (owners 1–4: Support, Natars, Nature, Multihunter) pay no troop upkeep** in `Automation::bountycalculateProduction()`. Charged upkeep, a Wonder village produces ‑45k crop/h and the Natar capital ‑5.2M crop/h, against a ceiling of ~165k/h that no field layout can reach — so they can never hold crop and their garrison is on a countdown.
- **`starvation()` also skips owners 1–4**, belt and braces. Before that existed, the *first* attack on a Wonder village — a failed scouting run was enough, since `updateRes()` runs for every resolved attack — credited weeks of negative crop at once and starvation emptied the whole garrison in ~10 minutes, so the next attacker walked in without a casualty.
- **They must stay lootable**, as in official T4 where Natar villages are ordinary raid targets. `natarProvisionVillage()` puts all 18 fields at level 10 (the official Wonder-village layout) plus warehouse/granary, precisely so `stored − cranny` is positive; with the installer's bare 800 storage against a level‑10 cranny (10,000/resource here) every raid returned 0 forever.

Regression cover: `tools/check_natar_starvation.php`, `tools/check_natar_lootable.php`, `tools/check_natar_attacks.php`.

### Templates
`.tpl` files are **plain PHP includes**, not a template engine — they mix HTML and `<?php ?>` and read the same globals. Edit them like PHP.

### Localization
`GameEngine/Lang/{es,en,de,ru,fa}.php` each define UI text as `define()` constants plus a `$lang` array. `es.php` (Spanish) is the active target locale; translation from the English original is an **ongoing effort** — player-facing pages are done, the Admin panel is the main remaining English area. Use neutral/LatAm Spanish, not peninsular terms.

### Admin panel
The **live** admin panel is `Admin/admin.php` → `Admin/Templates/`. The old duplicate entry points (`Admin/index.php`, `Admin/tpl/`, `Templates/Admin/`, …) were removed; if you find another copy, it is dead.

## Conventions & gotchas

- **Timezone is hard-coded** `America/Argentina/Buenos_Aires` (in `Village.php` and docker-compose), matching the Docker `TZ`.
- The web container runs Apache as **UID 1000** so it can write the bind-mounted code and `config/` / `install/installconfig/`. Permission errors on those paths usually trace back to a UID mismatch.
- `config/connection.php`, `config/installed`, `.env`, and `backup-*.sql` are gitignored; never commit generated config or secrets.
- Do **not** touch any sibling `travian-*` Docker containers on this host — only the `traviant4-php7` stack belongs to this project.
- Sidebar layout is fragile: never widen `#side_info` in `compact1.css` (it's a 196px float inside the 990px `#mid`, so widening it breaks the float layout). The signs *inside* it may overflow to the right, which is fine.
- **Wooden signs.** A sign's width used to be baked into its `gpack/.../img/layout/sign*.png` art. Three of them are now width-independent instead: `#villageList` (the village list), `#villageName` (the current village's name) and `#cultureProgress` (the culture panel, which borrows the village list art) all set `background-size:100% <h>px`, so the PNG stretches to whatever width the element takes. Consequences worth knowing:
  - Width comes from the content: `width:max-content` clamped by `min-width`/`max-width`. Keep the clamps within roughly ±25% of the art's native width or the nails start looking stretched.
  - `#villageList ul a:after{content:attr(data-name)}` is an invisible zero-height copy of the name in bold, so the measured width doesn't change with which village is active (the active one renders bold). Keep `data-name` in `Templates/multivillage.tpl` in sync with the link text.
  - `#villageName` grows in both directions: it's `left:85px` + `translateX(-50%)`, i.e. anchored by its centre rather than its left edge.
  - `#cultureProgress` builds the sign out of three real boxes (`.cultureProgressSign{Top,Body,Foot}` in `Templates/culture_progress.tpl`), with the body's negative margins reclaiming the parchment part of each roll. The container must stay backgroundless: the roll art is transparent outside the sign outline, so a background on the container shows through above the top roll and below the bottom one as a pale band. Its right edge must stay under x=293 of the viewport, where the leftmost dorf1 resource badge sits.
  - Both `#villageName` and `#cultureProgress` hang past the left edge of the 990px wrapper and get re-anchored by a `max-width:1119px` media query. That threshold is `990 + 2*maxOverhang + 20`: a media query measures the viewport *including* the scrollbar while the wrapper is centred in the width without it, so the breakpoint must also cover the scrollbar or the sign is clipped in a ~20px band of window widths.
  - Re-splice the art only if a sign needs a genuinely different native size: `tools/widen_sign.php <villages|vname> <ancho>` stretches the smooth parchment bands and leaves nails, screws and the arrow tip alone. It only stretches, never shrinks, and needs the original art restored first.
- **Commit style:** the commit must be **only a title** — short, in English, no body/description. The author is always the repo user (Matias); **never add a `Co-Authored-By` trailer or any other co-author**.

## Deployment note

Production is **travian.chewer.net**, served from a **Raspberry Pi 4B (8GB RAM)**, separate from local Docker. **Every push to git triggers `deploy.sh` on the Pi** (`git pull` + `docker compose up --build --detach`), so pushed changes go live automatically — treat `origin/master` as production. The redeploy is **near-instant**: the compose stack is just MariaDB + PHP and the game source is bind-mounted as a volume, so PHP/template edits apply immediately and the image only actually rebuilds when `docker/Dockerfile` or `docker/php.ini` change (rare, and the only case where the ARM/8GB slowness matters).

**Cloudflare sits in front of travian.chewer.net** and caches static assets for 4 hours (`cache-control: max-age=14400`). PHP output isn't cached, but CSS, JS and images are, so a deployed asset change is invisible until the TTL expires *unless the URL changes*. Every static asset referenced from a template or a stylesheet needs a version query when its content changes — including images referenced from inside CSS (`url(...png?v=N)`), which is the easy one to forget: bumping only `compact.css?asd…` ships new rules against stale art. To check what production is really serving, request the asset with a throwaway query (`?x=1`) to bypass the edge cache and compare against the plain URL; `cf-cache-status: HIT` in the headers means you're looking at the cache, not the origin.

**Never request the new versioned URL until the deploy has actually landed.** Fetching `…?v=37` while the Pi is still pulling caches the *old* file under the *new* key, and every player then gets new HTML against stale CSS for the full 4 hours — worse than not bumping at all. Poll the origin with throwaway queries first (`until curl -s '…/compact.css?bypass=$RANDOM' | grep -q 'v=37'; do sleep 4; done`), and only touch the real versioned URL once that passes. If a key does get poisoned, the self-service fix is to bump to a fresh one.

Schema changes that the installer would normally create must be applied to the prod DB manually (see `tools/migrations.sql`).
